## 老步兵配置移植到 H7_BSP（分支 `老步兵测试`，提交 `cb05beb`）

把 `~/code/project/rm/demo`（老步兵，单 `main` 分支，工作区 4 个文件未提交）的机器人
逻辑移植进 H7_BSP 的 Application 层，采用「就地改造 + 宏区分两套实现」方案。

### 关键架构事实

- 老步兵是**双板架构**：底盘板（本次移植目标）负责底盘电机、SBUS 遥控、姿态解算，
  并经 FDCAN2 用 `0x065/0x070/0x075` 把遥控与状态转发给独立的**云台板**；发射机构
  由云台板负责，底盘板不碰。
- 底盘板硬件：FDCAN1 挂 4 路 DM 速度模式底盘电机（节点 `0x50~0x53`，接收 ID
  `0x60~0x63`）+ 1 路 DM MIT 云台电机（节点 `0x03`，接收 ID `0x05`）；SBUS 走 UART5。
- 框架的 UART5 早已按 SBUS 参数配置（100000 / 9B / 偶校验 / 2 停止位 / 仅 RX，
  引脚宏 `SBUS_TX__UART_RX_Pin`，DMA2_Stream3），移植时无需改外设。

### 落点

| 内容 | 位置 |
| --- | --- |
| 整机开关 `H7_LEGACY_INFANTRY`（与 `H7_APP_*` 互斥） | 根 `CMakeLists.txt` |
| 遥控输入适配 + 健康互锁 + 云台跟随 + 板间链路 | `Application/Communication/Com.*` |
| DM 四电机麦轮底盘分支 | `Application/Chassis/Chassis.cpp` |
| DM MIT 单轴云台分支 | `Application/Gimbal/Gimbal.*` |
| SBUS 设备（复用 UART BSP 双缓冲） | `Device/Peripheral/Remote/sbus.*` |
| 云台板下行帧 | `Device/Peripheral/GimbalBoard/gimbal_board.*` |
| 速度规划算法 | `Middleware/Algorithm/SpeedPlanning/SpeedPlanning.*` |

### 关键决策与坑

- **控制周期差异**：demo 是 2 ms，框架是 1 ms。速率限制的单位是「速度单位/秒」，
  所以把 `*_CONTROL_DT` 改成 `0.001f` 后每秒加减速特性与 demo 一致，无需改限制值。
- **DM 节点 ID 超范围**：`Class_DMMotor::Init` 原本限制 `can_id <= 0x0F`，而老步兵用
  `0x50~0x53`。已放宽到 `0xFF`，并把反馈匹配从 `data[0]&0x0F == can_id` 改为比较
  低 4 位（由 `master_id` 保证唯一性）。对原有 `0x00~0x0F` 配置行为不变。
- **C/C++ 链接**：框架的 `bsp_uart.h` 没有 `extern "C"`，C 文件调用 `UART_Init` 会
  链接失败，所以 `sbus` 用 `.cpp` 编译单元。
- **安全互锁的框架化**：demo 的 `SafetyTask`（整板使能门控）映射为「未解锁时每周期
  显式下发 `ZERO_FORCE` + `GimbalMode::DISABLED`」，而不是复刻整板门控。
- 原 `Chassis_Analysis_Vel` 会把轮速组合结果强转 `int16_t` 再赋回 `float`，本次保留
  浮点精度（已在文档标注差异）。

### 有意未移植

## 补充：用户追问"是否全部适配"后的核查（提交 `450d32d`）

### 补上的遗漏

- **WS2812 武装指示灯**：上轮只做了健康互锁状态，漏了驱动指示灯。demo 语义是
  「红灯 = 电机失能，蓝灯 = 已解锁」，在 `SafetyTask` 状态跳变时切换，上电默认红。
  已接入 `Communication::Communication_UpdateArmState`。框架内无其他模块争用灯色，
  所以只在状态变化时设置即可，不需要像 demo 的 `DebugTask` 那样每帧重申。

### 核查结论（重要，供后续参考）

- **FDCAN 两边等价**：demo 80MHz/PSC=1、框架 120MHz/PSC=3，位时间都是 1 Mbps、
  采样点都是 75%。`MessageRAMOffset` 与 `AutoRetransmission` 不同但不影响互通。
- **UART5 的 SBUS 参数两边完全一致**，底层不用动。
- **框架 BMI088 是 demo 的超集**：C++ 类化之外还修了两处（PRIMASK 恢复方式、
  `Init_Finished_Flag` 加 volatile）；但丢了 5 个 C 接口（`BMI088_Get_Yaw_Rate` 等），
  等价能力在 `sys_imu.cpp` 的 `System_IMU_Publish_State` 里。
- **`alg_basic` / `alg_filter_vqf` / `alg_matrix` / `alg_quaternion` / `bsp_spi`
  两边源码完全相同**，属同源抽取，无需移植。
- **demo 里的死代码**：`User/algorithm/PID.c` 无任何调用者；`Booster_Left/Right_ID`
  只有定义无引用；`bsp.h`/`device.h`/`bsp_def.c` 是空模板。都不要移植。
- **VQF 参数差异待定**：demo 用 `alg_filter_vqf.h` 里的默认值（`Rest_Threshold_Gyro_Deg_S
  = 2.0`），框架在 `System_IMU_Configure()` 里显式配成 3.5。阈值越大越容易判静止、
  零偏估计越激进。老步兵若要复现 demo 行为需改 `sys_imu.cpp`，但这是整机级参数，
  改动会影响所有配置，建议实车确认后再定。
- **未移植且判断为合理**：`DebugTask` 的遥测打印、`WitGyro`（含 `uart_bsp.c` 的 WIT
  DMA 分支）、`ElegantDebug` —— 三者在 demo 中都只服务于调试显示，不参与控制回路，
  且框架已有 `sys_debug` / EricTool 通道。

## WS2812 不亮的诊断（提交 `9e9f10a`）

### 现象与根因

上电后 WS2812 完全不亮。根因不是代码：**烧的是 `build/Debug`（默认配置，
`H7_LEGACY_INFANTRY=OFF`），该固件里没有一行老步兵代码**。

符号表对比是决定性证据：

| 符号 | build/legacy | build/Debug |
| --- | --- | --- |
| `Communication_IndicateArmed` | 有 | **无** |
| `Communication_Armed` | 有 | **无** |
| `SBUS_Init` | 有 | **无** |
| `Communication_Init` | 正常实现 | 空实现（地址紧跟 `Communication_Update`）|

默认配置下 `BSP_WS2812.Init()` 是无参调用（颜色默认黑色），且没有任何地方调用
`Set_RGB`，所以灯保持熄灭——这是框架原本的正常行为，不是故障。

### 为什么容易烧错固件

本机 **`/tmp` 是 10 MiB 的 tmpfs**（`tmpfs 10M`），而根分区有 219G 空闲。GCC 为大
文件写临时汇编时会超过 10 MiB：

```
fatal error: error writing to /tmp/ccXXXX.s: No space left on device
```

结果是 **legacy 全量构建失败、Debug 增量构建却能成功**，手上只有默认配置固件可用。
已在根 `CMakeLists.txt` 加 `-pipe` 根治（编译阶段间走管道，不落临时文件），并新增
`LegacyInfantry` preset 输出到 `build/legacy`，让老步兵固件有明确构建入口。

### 与老工程逐项对比的结论

**完全一致**（这些都不是原因）：SPI6 引脚 PA5/PA7、SPI6 时钟源（PLL2 50 MHz）、
分频 `/8`、位编码 `LEVEL_0=0x60 / LEVEL_1=0x78`、GRB 编码与 25 字节帧格式、
SPI6 的阻塞式发送路径、5V 使能引脚（框架 `DC5__OUTPUT` 与老工程 `OPEN_5V` 同为 PC15）。

**唯一的真实差异**（已修复）：发送时机。

| | 老工程 | 框架（改前） |
| --- | --- | --- |
| `Init` | 设色 + **立即发送一帧** | 只设颜色 |
| `Set_RGB` | 设色 + **立即发送一帧** | 只改颜色缓存 |
| 周期刷新 | 10 ms 回调 | TIM 10 ms 分发 |

老工程是"设置即发送 + 周期刷新"双保险，框架只有周期刷新。已在
`Communication_IndicateArmed()` 里补一次即时刷新，使武装状态跳变时灯色立刻可见。

### 若烧了 legacy 固件仍不亮

代码与底层配置已逐项核对完毕，剩下的排查方向是硬件：灯珠供电、灯珠型号与数量、
PA7 是否有实际波形（示波器/逻辑分析仪），以及**同一块板跑老工程固件时灯是否亮**。
另外需确认烧录目标是达妙 MC-02 板还是老步兵原板——若是后者，所有引脚定义都要重新核对。

## 底盘两个轮子不动：CAN 总线饱和（提交 `7c2ba29`）

### 现象与根因

实车反馈：底盘有两个轮子不响应，且同一辆车跑老工程固件时一切正常。

根因是**移植时只改了周期、没改下发频率**，把 CAN 负载翻了一倍：

| | 老工程 | 移植初版（1 kHz） | 修复后（2 ms） |
| --- | --- | --- | --- |
| 控制周期 | 2 ms | 1 ms | 2 ms |
| 每周期帧数 | 8 | 8 | 8 |
| 实际负载 | **4 帧/ms** | **8 帧/ms** | **4 帧/ms** |
| 总线余量 | 充足 | **超载** | 充足 |

1 Mbps 下标准数据帧含位填充约 133 µs，**理论上限约 7.5 帧/ms**，8 帧/ms 必然过载。
帧数构成：4 路 DM 底盘速度帧 + 1 路 DM 云台 MIT 帧 + 3 路板间帧。

`BSP_CAN_SendPer` 的行为放大了后果：它遍历 32 个槽、失败时**保留待发状态下轮重试**
（不丢帧），但在持续过载下 FIFO 每次都被填满，排在轮询顺序后面的帧长期发不出去——
所以表现为**固定的几个电机不响应**，而不是随机丢帧。

> 框架默认的 AGV 路径不会暴露这个问题：DJI 电机是 4 个一帧打包，帧数远少于 DM 的
> 每电机一帧。

### 修复

- `Chassis`：`CHASSIS_CONTROL_DT` 回到 `0.002f`，控制路径按 2 分频执行
- `Gimbal`：`GIMBAL_CONTROL_DT` 回到 `0.002f`，同样 2 分频
- `Communication`：板间三帧改为 2 ms 下发，与老工程 `GimbalTask` 周期一致

速度规划的单位是"速度单位/秒"，所以 dt 与调用频率同步减半后，每秒加减速特性不变。

### 顺带修复

`Communication` 里云台反馈不可用时仍执行坐标旋转的问题：此时角度按 0 处理会被换算成
`-180°` 偏差，把底盘速度方向整个翻转。现已改为反馈无效时跳过旋转、跟随速度置 0。

### 教训

前几轮审查都是从"逻辑是否与老工程等价"的角度做的（通道索引、符号、运动学公式、
CAN ID、引脚、时钟），**漏掉了总线物理容量这个维度**。移植一个以 2 ms 为节拍设计的
控制链路到 1 kHz 调度框架时，周期本身就是需要显式处理的移植参数，不只是 dt。

修复后建议实测确认：四轮是否都响应、单推一个方向时各轮速是否符合麦轮公式。
